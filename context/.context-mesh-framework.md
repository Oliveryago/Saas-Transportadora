# Context Mesh Framework

## Overview

Context Mesh is a structured documentation system for AI agents working on software projects. It separates **intent** (what and why) from **decisions** (how and why technically) from **patterns** (how to implement).

## The 3 Steps

1. **Intent** — Define WHAT the project/feature does and WHY it exists (business value)
2. **Build** — Document HOW it was built (technical decisions, patterns)
3. **Learn** — Record outcomes, lessons, and evolution

## File Type Separation Rules

### Feature Files (`intent/feature-*.md`)
- **WHAT** the feature does — functional description from user perspective
- **WHY** it exists — business value, user need
- **Acceptance criteria** — functional requirements
- ❌ NO technical details, library names, code examples

### Decision Files (`decisions/*.md`)
- **Technical choice** made (which library, approach, architecture)
- **Rationale** — why this approach over alternatives
- **Alternatives considered**
- Links back to feature files

### Pattern Files (`knowledge/patterns/*.md`)
- **Code examples** showing how to implement
- **When to use** the pattern
- **Files using** the pattern
- Links to related decisions

### Agent Files (`agents/*.md`)
- Instructions for specialized AI agents
- Task-specific context and rules

## Plan, Approve, Execute (MANDATORY)

Before implementing ANY significant change:
1. **Plan** — Create or update implementation plan
2. **Approve** — Get explicit user approval
3. **Execute** — Implement the approved plan
4. **Learn** — Update context with outcomes

## Context Structure

```
context/
├── .context-mesh-framework.md   ← This file
├── intent/
│   ├── project-intent.md        ← Project overview
│   └── feature-*.md             ← One per feature
├── decisions/
│   └── ###-*.md                 ← Numbered decisions
├── knowledge/
│   ├── patterns/
│   │   └── *.md                 ← Implementation patterns
│   └── anti-patterns/
│       └── *.md                 ← What to avoid
├── agents/
│   └── *.md                     ← Specialized agent instructions
└── evolution/
    └── changelog.md             ← History of changes
```

## When to Create Files

| Situation | File to Create |
|-----------|---------------|
| New feature or module | `intent/feature-[name].md` |
| Technical library/framework choice | `decisions/###-[name].md` |
| Recurring code pattern found | `knowledge/patterns/[name].md` |
| Bad practice to avoid | `knowledge/anti-patterns/[name].md` |
| Context updated | `evolution/changelog.md` entry |

## Bidirectional Links (Required)

- Feature → Decision: `- [Decision: Name](../decisions/###-name.md)`
- Decision → Feature: `- [Feature: Name](../intent/feature-name.md)`
- Feature → Pattern: `- [Pattern: Name](../knowledge/patterns/name.md)`
- Pattern → Decision: `- [Decision: Name](../decisions/###-name.md)`

## Definition of Done (Build Phase)

Before completing any implementation:
- [ ] Decision file exists (if technical choice was made)
- [ ] Code follows documented patterns
- [ ] Relevant feature file updated if scope changed
- [ ] Changelog updated
- [ ] Tests passing (if applicable)

## Status Values

- `Active` — In use, up to date
- `Accepted` — Decision made and implemented
- `Deprecated` — No longer recommended
- `Proposed` — Under consideration
- `Superseded` — Replaced by newer decision
